# MetricTrust

SQL data quality gates and payment reconciliation.

## Executed result

Ran **22 checks** across **550,688 source rows**. There were **3 warning categories and 0 blocking errors**. The naive join produced **BRL 20,308,134.71**, versus **BRL 16,008,872.12** at payment grain: **26.86% inflation**. This is a demonstrated query error, not recovered money. All six injected defect classes were detected.

## What it does

Runs 22 declarative SQL checks over seven Olist source tables and exports record-level exception CSVs. Checks primary keys, foreign keys, amounts, chronology, review scores, incomplete deliveries, missing items and payment reconciliation. Each rule records severity, affected-record count, pass/fail status, and executable SQL in `rules.json`.

The reconciliation aggregates items and payments independently at order grain. A diagnostic report contrasts that result with a naive item/payment join to reveal duplicated financial totals. Amount reconciliation allows BRL 0.05 rounding tolerance. Failed-record counts across rules overlap and must not be added as unique defective records. Unparseable amounts are reported separately; diagnostic sums omit them.

## Run

```bash
pip install -r requirements.txt
python app.py demo --raw data/demo --output results/demo
python app.py download --raw data/raw
python app.py audit --raw data/raw --output results --strict
# Copy the inputs and inject six known defect classes; originals are preserved:
python app.py inject --raw data/raw --output results/injection
python -m http.server 8001 --bind 127.0.0.1 --directory results
```

Open http://localhost:8001/dashboard.html. `--strict` exits 2 on any failing error-severity rule, and 0 when only warnings or no failures remain. This lets a scheduler block downstream reporting on critical defects. The injection command verifies that all six intended rule failures were detected and writes injection_validation.json. Secondary failures can occur too; this is a deterministic fault-injection test, not a statistical accuracy benchmark.

Real-data warnings are investigation items, not proven corruption: canceled/unavailable orders can lack items; payment discrepancies may reflect dataset semantics. Do not automatically delete or “correct” them. The real source and injected test source have separate manifests. Rules are trusted local SQL configuration and should never be accepted from anonymous HTTP requests.

## Outputs

- `results/metrics.json`: rule results, timing, source checksums and environment.
- `results/quality_summary.csv`: one row per rule, ready for Excel or Power BI.
- `results/exceptions/*.csv`: evidence for each check, including zero-row headers.
- `results/dashboard.html`: searchable quality report.
- `powerbi/measures.dax`: optional Power BI authoring template; it has not been executed in Power BI Desktop.
